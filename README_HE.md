# החנוכיאדה המשפחתית הגדולה

אפליקציית ווב מלאה בעברית וב־RTL להפעלת ערב משחק משפחתי: חדר עם קוד ושיתוף קישור/QR, הצטרפות משתתפים ללא התקנת אפליקציה, חידון ארבע אפשרויות עם ניקוד בצד השרת, סבבי תמונה, שאלות משפחתיות, משימות סודיות, גלגל מזל, לוח תוצאות וקבוצות.

## מצב הפרויקט והבטחות

זהו פרויקט מקור עובד שמוכן לחיבור לפרויקט Supabase שבבעלות המארח ולהעלאה לאחסון סטטי. אין בקובץ הזה חשבון Supabase, כתובת חיה, מפתח, נתוני משפחה או חדר פעיל. לכן כרגע **אין קישור חי**, וסנכרון לא יעבוד עד השלמת ההגדרה בפרק הבא. לא הוצג כאן מצב דמו עם ניקוד מקומי.

הסנכרון משתמש ב־Supabase Realtime דרך `room_events`; יצירת חדר, שיוך מנהל, צירוף שחקן, פתיחת/סגירת סבב, בדיקת תשובה וניקוד מתבצעים ב־PostgreSQL RPC. מפתח תשובות וטבלת התשובות אינם קריאים ישירות לשחקנים. הגבלת תשובה אחת היא לפי זהות חשבון Supabase של המשתתף בכל סבב. מי שיוצר חשבון אנונימי חדש או מחליף מכשיר/דפדפן עלול להיראות כמשתתף נוסף; אין זיהוי אנושי חסין־עקיפה. המנהל יכול לתקן ניקוד דרך המסך.

מוגדר גבול של עד 120 משתתפים בחדר, אך אין בדיקת עומס ל־100 משתתפים ולא נבדקה התקנה על מכשירי iPhone/Android אמיתיים. יכולת 100 משתתפים תלויה בתוכנית, במגבלות ובאזור של פרויקט Supabase ובבדיקת עומס לפני האירוע. אפליקציית PWA יכולה להתווסף למסך הבית, אך פתיחת חדר והצטרפות/סנכרון מחייבים אינטרנט; קבצי הממשק נשמרים מקומית בדפדפן לאחר טעינה, לא מנגנון משחק אופליין.

## מה עובד בקוד

- יצירת חשבון מארח/כניסה בדוא״ל ובסיסמה; המארח רואה רק את חדריו.
- יצירת חדר עם קוד, קישור QR והצגת רשימת נוכחים חיה.
- צירוף משתתפים עם שם וקבוצה; חידוש מושב באותו דפדפן כאשר Auth שומר את המושב. אחרי רענון הדף, קוד החדר והשם/הקבוצה נשמרים זמנית ב־`sessionStorage` כדי למלא מחדש את טופס ההצטרפות; צריך ללחוץ שוב על הצטרפות כדי לטעון מחדש את מצב המשחק.
- מאגר פתיחה של 35 שאלות חנוכה, היסטוריה, תפילה ומנהגים, בשלוש רמות קושי; המנהל יכול לערוך, להוסיף ולמחוק שאלות.
- חידון, שאלת משפחה, סבב „מי בתמונה?” עם תמונה פרטית, וסבב גמר — כל אלו משתמשים במנוע השאלות והניקוד המשותף.
- מגבלת זמן לבחירה: 30 שניות, דקה, דקה וחצי או ללא הגבלה. השרת דוחה תשובות לאחר המועד, והדפדפן של המנהל סוגר את הסיבוב כשנגמר הזמן; בונוס המהירות מחושב ומוגבל בשרת.
- סגירת סבב חושפת תשובות נכונות ותוצאות. נשמר הסיבוב האחרון, כולל תוצאת הגלגל, כך שכל המשתתפים רואים את התוצאה גם לאחר שהסיבוב נסגר.
- משימות סודיות נשלחות לשחקן אחד, והשלמה מזכה פעם אחת ב־200 נקודות.
- גלגל המזל בוחר משתתף יחיד בשרת לסיבוב, והתוצאה נשארת מוצגת למנהל ולמשתתפים.
- המנהל יכול לסגור ולפתוח מחדש חדר, או לאפס סיבובים, תשובות, משימות וניקוד תוך שמירת רשימת המשתתפים ומאגר השאלות. האיפוס דורש אישור מפורש במסך.
- ניקוד משפחות/קבוצות מוצג בנוסף לטבלת היחידים; המארח יכול לשנות שיוך לקבוצות ולתקן ניקוד. סבב הגמר מכפיל ניקוד תשובה נכונה.
- תמונות נשמרות ב־bucket פרטי, והמארח מעלה; שחקנים בחדר מקבלים קישור חתום זמני להצגת תמונת הסיבוב.

## הקמה — פעם אחת

1. צרו פרויקט חדש ב־[Supabase](https://supabase.com/dashboard). בחרו סיסמת DB חזקה ושמרו אותה מחוץ לקוד.
2. ב־Supabase Dashboard → SQL Editor הריצו את המיגרציות לפי הסדר:
   - מסד חדש: `20261117120000_initial_schema.sql`, ואז `20261117190000_reliability_audit.sql`.
   - מסד קיים מהגרסה הקודמת: אל תריצו שוב את קובץ ההקמה; הריצו פעם אחת את `20261117173000_game_improvements.sql`, ואז `20261117190000_reliability_audit.sql`.
   המיגרציה האחרונה מעדכנת רק את פעולת שליחת התשובה. אם המסד כבר קיבל אותה, אין להריץ אותה שוב ללא צורך.
3. ב־Authentication → Sign In / Providers: הפעילו Email (למארח) ו־Anonymous sign-ins (למשתתפים). הגדירו אישור כתובת אימייל לפי בחירתכם; אם האישור מופעל, המארח צריך לאשר את המייל לפני כניסה. אל תבטלו אמצעי אבטחה בלי לשקול את הסיכון.
4. בפרטי הפרויקט העתיקו את ה־Project URL ואת המפתח הציבורי `anon` / `publishable` (לעולם לא `service_role`).
5. צרו עותק בשם `.env.local` מתוך `.env.example` ושימו בו את הערכים:
   ```env
   VITE_SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
   VITE_SUPABASE_ANON_KEY=YOUR_PUBLIC_ANON_OR_PUBLISHABLE_KEY
   ```
6. התקינו Node.js 20 ומעלה, ואז בתיקיית הפרויקט הריצו:
   ```bash
   npm install
   npm run build
   npm run dev
   ```
   למחשב האישי כתובת הפיתוח תופיע במסוף. אין להזין בו פרטים אמיתיים לפני חיבור הפרויקט הפרטי שלכם.

## פרסום קישור ו־QR למשפחה

קובץ `vercel.json` מגדיר התקנה עם pnpm, פקודת build ותיקיית `dist`, וכן מונע שמירה ממושכת של קובץ ה־service worker. ייבאו את התיקייה ל־Vercel והגדירו את `VITE_SUPABASE_URL` ואת `VITE_SUPABASE_ANON_KEY` בהגדרות הפרויקט. לחלופין העלו את `dist` לאחסון סטטי אחר בכתובת HTTPS בשליטתכם. כוונו ב־Supabase → Authentication → URL Configuration את Site URL ו־Redirect URLs לדומיין הזה. לאחר פרסום, פתחו את הדומיין, התחברו כמארח, צרו חדר והציגו את ה־QR/קישור שנוצר. ה־QR באפליקציה משתמש בדומיין הנוכחי; קוד `localhost` מתאים רק למחשב שלכם.

**אין כרגע דומיין או שרת ציבורי שנוצרו עבורכם.** כדי לקבל קישור חי יש להשלים פרויקט Supabase וחשבון אחסון/דומיין; זה גם מונע ממני להמציא קישור או לטעון שהמשפחה יכולה להיכנס לפני הגדרה.

## הרשאות ופרטיות

- ה־`anon/publishable key` הוא מפתח ציבורי, ומותר לשים אותו ב־frontend רק יחד עם RLS ופונקציות ההרשאה שבמיגרציה. לעולם לא לשים `service_role`, סיסמת DB או מפתח ניהול בקובצי `VITE_*`, בקוד, ב־ZIP או ב־GitHub.
- אימות מנהל נעשה ב־Supabase Auth. משתתפים משתמשים בכניסה אנונימית. פונקציות RPC בודקות חדר/מנהל/משתתף; שחקנים אינם קוראים את מפתח התשובה או טבלת התשובות.
- תמונות נשמרות ב־bucket פרטי, עד 8MB ל־JPG/PNG/WebP; קישור צפייה חתום תקף 30 דקות ומתחדש כל 25 דקות כל עוד המסך פתוח. מחיקת שאלה שכבר שוחקה חסומה כדי לא למחוק היסטוריית משחק.
- נשלחים ל־Supabase שמות המשתתפים, שמות הקבוצות, התשובות, הניקוד והתמונות שנבחרו. השתמשו רק בתמונות ובמידע שאתם מורשים לשתף, והגדירו מדיניות שמירה/מחיקה בפרויקט.
- RLS מגן מפני גישה ישירה לא מורשית, אך לא מצפין נתוני אפליקציה בקצה־לקצה; ספק ה־Backend מארח את המידע. אל תכניסו מידע רגיש שאינו נחוץ.

## ביקורת טכנית ובדיקות

במהדורת הביקורת נשמר העיצוב ומבנה המשחק; קובץ המקור שהתקבל נשאר ללא שינוי, והשינויים נמצאים בעותק ZIP נפרד.

- פעולת שליחת תשובה משתמשת כעת בנעילת קריאה משותפת לסבב, כך שתשובות של שחקנים שונים אינן ננעלות זו אחר זו על אותה שורה. אינדקס ייחודי יחד עם `ON CONFLICT DO NOTHING` מונעים ניקוד כפול גם כשאותו שחקן שולח שוב במקביל; בחירה חסרה/לא חוקית נדחית במפורש.
- בעת רענון הדף טופס ההצטרפות נטען מחדש עם קוד החדר ושם/קבוצה שנשמרו ב־`sessionStorage`. המשתתף לוחץ מחדש על הצטרפות; חשבון Auth הקיים משייך אותו לאותו כרטיס שחקן ומצב המשחק נטען מהשרת.
- `pnpm install --frozen-lockfile` ו־`pnpm run build` עברו לאחר השינויים.
- הרצתי את מיגרציית ההקמה, שדרוג המשחק ומיגרציית הביקורת על PostgreSQL מקומי. בתרחיש בדיקה זמני של מנהל ושני משתתפים אומתו: 35 שאלות, גישת שחקן חסומה לשאלות/מפתחות תשובה דרך קריאות RPC/טבלה, תשובה ראשונה מתקבלת, ניסיון חוזר מקבל `duplicate` בלי ניקוד נוסף, שחקן שני מקבל ניקוד, וסגירת הסבב חושפת תוצאות. נתוני הבדיקה נוצרו בתוך טרנזקציה שבוטלה.
- ההתקנה המקומית הציגה אזהרת `wal_level` שאינה מאפשרת לבדוק Realtime עם מופע PostgreSQL הזה. לא נבדקו חיבור/Auth/אחסון/Realtime של Supabase אמיתי, שני מכשירים פיזיים, התאמה בפועל ל־iPhone/Android, או עומס של 100 משתתפים. הגבלת 120 בקוד אינה הוכחת קיבולת.
- לפני משחק אמיתי עדיין צריך להגדיר Supabase ו־Vercel, לוודא את RLS וה־Auth בפרויקט שלכם, לבדוק QR והצטרפות על מכשירים שונים, להתנסות בניתוק וחזרה, ולהריץ בדיקת עומס בסביבת בדיקה נפרדת.

## מבנה

- `src/` — ממשק React בעברית ו־RTL, חיבור realtime ופעולות.
- `supabase/migrations/20261117120000_initial_schema.sql` — הקמת מסד חדש, RLS ופעולות משחק בצד השרת.
- `supabase/migrations/20261117173000_game_improvements.sql` — עדכון מסד שהוקם מגרסה קודמת בלי למחוק חדרים ונתונים.
- `supabase/migrations/20261117190000_reliability_audit.sql` — שליחת תשובות בטוחה לעומס מקביל ומניעת ניקוד כפול.
- `vercel.json` — פקודות build והגדרות פריסה ל־Vercel.
- `.env.example` — שמות משתני הגדרה בלבד, ללא ערכים סודיים.
- `public/` — manifest ואייקון PWA.

הקוד אינו מפרסם ל־GitHub בעצמו. ה־ZIP המלא מכיל את הפרויקט והוראות ההקמה; לא נכללים בו מפתחות, חשבונות, נתוני בני משפחה או כתובת חיה.
